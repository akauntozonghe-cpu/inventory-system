# 現役DBと廃止記録の分離 — 関連機能監査と移行設計
2026-11-23 / Inventory OS / 状態: **段階修正中（物理的分離は未実装）**

## 原則
- 現役テーブルだけが通常業務の唯一の参照元。現役の登録・編集・統合・検索・一覧・選択・印刷は、存在する有効なIDに制約する。
- 廃止は「履歴だけを残したステータス」ではなく、**現役レコードを保管用の別テーブル/スキーマへ移す業務**。
- 廃止記録は不変のJSONBスナップショットと識別情報、操作記録。通常業務の一意制約・外部キー・件数判定から独立する。
- 再登録は復元ではなく、新規登録処理へスナップショットを事前入力する。新IDを生成し、現在の制約で検証。旧記録は消さず、旧ID/新IDの対応を監査記録する。
- 在庫の数量、棚卸値、履歴は自動で再登録しない。現物確認が必要。

## 参照関係の扱い
現役領域にレコードが残る限り、完全分離ではない。特に場所の廃止時には現役在庫のstorageLocationIdをどう扱うか決めてから移行する必要がある。
- 現役在庫が廃止場所を使っている場合、現在のFKを残したまま場所の行を消すことはできない。新場所へ移管するか、場所未設定へ切替えて旧場所の文字列とIDを監査/履歴スナップショットに保存する。**在庫移動を黙って実行しない。**
- 分類廃止時に現役商品・在庫の分類文字列が残っていると、現役データ整合性の原則と矛盾する。移管先選択または未分類化を廃止確認フローで行い、変更前の値を監査記録する。
- 未完了棚卸セッションの分類/場所スコープは先に再割当て・完了・保留などを判断。完了済みの履歴は絶対に書き換えない。
- 旧QRから検索するときは、現役として再利用させず「廃止記録（管理者のみ）」または明確な廃止表示に着地。無断で新規分類を作らない。

## 安全な移行順序（現行DBに破壊的SQLを即実行しない）
1. **読み取り監査**：現役/廃止/履歴の件数、無効なカテゴリ文字列、孤立FK、進行中棚卸、QRエイリアス、重複JAN等を集計。現時点で実データ検査は未実施。
2. **アーカイブ用構造を追加**：PostgreSQL別スキーマ/テーブルにimmutable snapshot、旧ID、種別、version、廃止日時/理由/操作者、checksum、復元記録を設ける。現役表との新規FKは作らない。
3. **履歴参照の独立化**：旧Item/Inventory/Location/Classification IDの履歴用IDまたはimmutable snapshotsを設け、既存履歴と一致することを照合。
4. **二段階トランザクション移管**：現役側の関連データ解決→記録保管→監査ログ→現役表から除外。全部成功するか、全部失敗する。競合と再実行の冪等性を保証。
5. **登録としての復元**：旧スナップショットから通常登録フォームへ事前入力。JAN重複は既存商品を優先。登録後は旧記録と新IDをリンクし、過去の数量・棚卸を複製しない。
6. **各APIの契約テスト・実データ検証**：検索/一覧/選択/QR/JAN/棚卸/保管場所/CSV/集計/通知/報告・再登録を跨いでテスト。プレビューと本番DBの移行は別判断。

## 現時点の適用範囲
- GitHubドラフトPRで、一般の保管場所GET、共通選択候補、ラベル印刷候補、通常商品・在庫登録時の分類検証と在庫一括保管場所変更を改善。
- **物理的なアーカイブ化と既存データの移行は未実装。** 既存の「廃止」操作はフラグ方式のままなので、完全分離したと報告してはいけない。
- DB移行には現役在庫への依存や履歴FKの変換が必要。テスト合格だけでは実在する旧データの安全性を保証できない。

## 受入条件
1. 廃止後、現役側の一意制約・利用件数・選択/印刷・検索に廃止記録が関与しない。
2. 廃止記録が現役表へ一件も残っていないことを実DBの件数比較で検証。
3. アーカイブ記録と監査/当時の在庫・棚卸・販売履歴が参照できる。
4. 廃止操作は管理者専用。再登録は通常の検証を通り、旧記録は不変。
5. 進行中作業の再開・競合・障害時ロールバックを検証。
6. すべてのAPIが同一の状態定義を参照することを自動テストと監査で確認。

## 管理者用の読み取り診断
- `GET /api/admin/archive-audit` は管理者だけに現役/廃止レコードの件数を返し、現役在庫の廃止場所依存・廃止商品依存・未登録分類参照を診断する。**データ変更は一切行わない**。
- `safeToMigrate` は一部の既知の障害条件のみであり、完全分離が安全に実行できるという許可ではない。履歴FK・旧QRの参照・移行後の実地確認は別途必須。
- 既存の商品の分類を変更する際、大分類が変わったら旧小分類を保持しない（小分類は再選択）。通常APIは有効な分類を参照してから書き込む。

## 検証制約
GitHub上のコードを読み、VercelのCIログを確認しているが、本番PostgreSQLの現物レコードや移行前バックアップの復元検証は実施していない。データを壊す変更を勝手に本番で実行しない。
